# مدونة أحمد المنجاوي

هذا المستودع هو مصدر المقالات الثابتة للمدونة. تُكتب المقالة مرة واحدة بصيغة ماركداون أو إم دي إكس، ثم تمر من عقد المحتوى نفسه في المعاينة والبناء النهائي.

## تجهيز بيئة العمل

1. اختر Node.js بالإصدار `24.19.0` المسجل في `.nvmrc`، مع npm بالإصدار `11.17.0`.
2. تأكد من الإصدارين:

   ```sh
   node --version
   npm --version
   ```

   يجب أن تكون النتيجتان `v24.19.0` و`11.17.0` بالضبط.

3. ثبّت الحزم من ملف القفل:

   ```sh
   npm ci
   ```

## إنشاء مقالة

ضع كل ملف مباشرة داخل `src/content/articles` دون تقسيمه إلى مجلدات حسب القسم. استخدم ماركداون (`.md`) افتراضيًا، ولا تستخدم إم دي إكس (`.mdx`) إلا عند الحاجة إلى المكوّن المعتمد الموضح أدناه.

ابدأ ملف ماركداون بهذه البيانات:

```md
---
title: "عنوان المقالة"
description: "وصف موجز مناسب لاكتشاف المقالة."
summary: "الخلاصة التي تظهر للقارئ."
section: "generalIssues"
author: "ahmedElMangawy"
slug: "عنوان-عربي-ثابت"
publishedAt: "2026-08-26"
draft: true
youtubeId: "dQw4w9WgXcQ"
references:
  - label: "اسم عربي وصفي للمرجع"
    url: "https://example.com/reference"
---

اكتب مقدمة المقالة هنا.

## العنوان الرئيس الأول

اكتب متن المقالة، واستخدم عنوانًا فرعيًا من المستوى الثالث عند الحاجة.

### عنوان فرعي تابع

اكتب التفصيل المرتبط بالعنوان الرئيس السابق.

## الخاتمة

اكتب خاتمة المقالة هنا.
```

كل الحقول السابقة مطلوبة ولا توجد قيمة افتراضية للحقل `draft`. يمكن إضافة `updatedAt: "2026-08-27"` عند وجود تحديث جوهري، بشرط ألا يسبق `publishedAt`. يجب كتابة التاريخين كسلسلة مقتبسة بالصيغة الدقيقة `"YYYY-MM-DD"`. لا يجوز أن يكون تاريخ المقالة العامة في المستقبل.

الحقل `references` اختياري. عند استخدامه، اكتب قائمة من مراجع تحتوي كل واحدة منها على `label` عربي وصفي غير فارغ و`url` مطلق يبدأ بـ`https://` ولا يحتوي اسم مستخدم أو كلمة مرور. تُرفض الروابط النسبية، وروابط `http://`، والروابط المشوهة، والبروتوكولات غير الموثوقة. لا تستخدم الرابط الخام اسمًا ظاهرًا للمرجع.

إذا حذفت `updatedAt` فلن يظهر سطر تحديث فارغ، وإذا حذفت `references` أو تركتها قائمة فارغة فلن يظهر عنوان أو حاوية أو مسافة محجوزة للمراجع.

ترتيب التأليف الكامل هو: مقدمة مباشرة، ثم عناوين من المستوى الثاني ومتن واضح، ثم عناوين من المستوى الثالث داخل أقسامها عند الحاجة، وأخيرًا `## الخاتمة`. تظهر `الخلاصة` من حقل `summary` قبل المقدمة تلقائيًا؛ لا تكررها داخل المتن، ولا تتخطَّ مستويات العناوين.

المفاتيح المسجلة المسموح بها:

- `section: "refutations"` لقسم **الردود والشبهات**.
- `section: "generalIssues"` لقسم **القضايا العامة**.
- `section: "scholarship"` لقسم **القسم العلمي**.
- `author: "ahmedElMangawy"` للمؤلف **أحمد المنجاوي**.

اكتب `youtubeId` كمعرّف فيديو يوتيوب مكوّن من 11 حرفًا فقط، وليس كرابط كامل.

## المعرّف والمسار العام

الحقل `slug` هو هوية المقالة الثابتة؛ تغيير `title` أو اسم الملف لا يغيّر المسار. يجب أن يكون مكتوبًا بصيغة Unicode NFC مسبقًا، وأن يتكوّن من حروف عربية وتشكيل وأرقام عربية أو إنجليزية، مع شرطة مفردة بين المقاطع. تُرفض الشرطات في البداية أو النهاية أو المكررة، والحروف اللاتينية، وعلامات الترقيم، والنقاط، والشرطة المائلة بنوعيها، وعلامة النسبة المئوية، ومحارف التحكم أو الاتجاه الخفية.

المسار النهائي دائمًا:

```text
/{معرّف-القسم-العربي}/{slug}/
```

مثال: `/القضايا-العامة/عنوان-عربي-ثابت/`. لا تُنشئ مسار معاينة منفصلًا؛ تستخدم المعاينة المسار النهائي نفسه.

## المسودات والمعاينة

- `draft: true` يجعل المقالة متاحة عمدًا في خادم التطوير فقط، ولا ينشئ لها ملفًا في البناء النهائي.
- `draft: false` يجعل المقالة عامة بعد نجاح التحقق، بشرط ألا يكون `publishedAt` في المستقبل.

شغّل المعاينة المحلية:

```sh
npm run dev
```

افتح المسار النهائي للمقالة. عند تعديل الملف الأصلي وحفظه، حدّث الصفحة لترى التغيير من المصدر نفسه.

## استخدام إم دي إكس

ماركداون هو الخيار الافتراضي. المكوّن الوحيد المعتمد داخل ملفات `.mdx` هو `ContractNote`، ويُستخدم دون أي استيراد:

```mdx
<ContractNote>اكتب الملاحظة هنا.</ContractNote>
```

تُرفض داخل المقالات جميع عبارات `import` و`export`، ووسوم `script` و`iframe`، وأي مكوّن آخر غير معتمد. لا تضف استيرادًا للمكوّن داخل ملف المقالة؛ خريطة المكونات المشتركة توفّره تلقائيًا.

## التحقق والبناء

نفّذ الفحوص منفردة عند الحاجة:

```sh
npm test
npm run check
npm run build
npm run preview -- --host 127.0.0.1
npm run test:browser
```

وقبل اعتماد أي تعديل، نفّذ البوابة الكاملة:

```sh
npm run verify
```

تُشغّل هذه البوابة اختبارات عقد المحتوى، وتشخيصات Astro، ثم البناء الثابت واختبارات المتصفح على مساري ماركداون وإم دي إكس. أي حقل أو مسار أو صيغة إم دي إكس غير صالحة توقف العملية برسالة تحدد المصدر والقاعدة المخالفة.

كل تقارير المتصفح ولقطاته وآثاره وملفاته المؤقتة تُحفظ داخل `.artifacts` فقط. لا تنقل أدلة الاختبار إلى `src` أو `tests` أو `.planning`.

## لوحة النشر Sveltia CMS

لوحة النشر العربية موجودة في `/admin/` وتحوّل الحقول إلى ملفات ماركداون داخل المستودع نفسه، وتثبّت لغة Sveltia على العربية بصرف النظر عن لغة المتصفح. لا توجد قاعدة بيانات، ولا خادم تطبيق للموقع العام، ولا كلمة مرور خاصة بالمدونة. يبقى الموقع العام بناءً ثابتًا، وكل حفظ من اللوحة ينشئ طلب سحب للمراجعة قبل وصوله إلى `main`.

يربط المستودع لوحة الإدارة العامة `https://ahmed-almangawy.de5.net/admin/` بالمستودع العام `MohammedGhazal09/blog` وبـWorker المملوك على `https://mangawy-sveltia-cms-auth.ahmed-el-mangawy-blog.workers.dev`. يطلب OAuth صلاحية `public_repo` فقط. يبقى تسجيل الدخول **مغلقًا افتراضيًا** حتى يستبدل المسؤول قيمة `Client ID` الاختبارية ويخزّن `Client secret` في Cloudflare؛ لا يُحفظ السر في Git أو ملف أو رسالة.

### إعداد الأمان مرة واحدة

ينفّذ المسؤول التقني هذه الخطوات بحضور المالك، ثم يستخدم المالك اللوحة وحده:

1. أمّن حساب GitHub الخاص بالمالك بمفتاح مرور أو مفتاح أمان. أضف وسيلة تحقق احتياطية مستقلة، واحفظ رموز الاسترداد الجديدة مطبوعة أو في مخزن مشفر غير متصل بالحساب. لا تجعل الرسائل النصية الوسيلة الأساسية، ولا تنشئ رمز وصول شخصيًا للوحة.
2. في GitHub افتح **Settings → Developer settings → OAuth Apps → New OAuth App**. استخدم `https://ahmed-almangawy.de5.net/admin/` صفحةً رئيسة، واجعل **Authorization callback URL** مساويًا حرفيًا لـ`https://mangawy-sveltia-cms-auth.ahmed-el-mangawy-blog.workers.dev/callback`. انسخ `Client ID` العام، وأنشئ `Client secret` دون وضع السر في ملف أو رسالة أو سجل أو لقطة شاشة.
3. افتح `workers/sveltia-cms-auth/wrangler.toml`:

   - استبدل `replace-before-deploy` بقيمة `Client ID` العامة.
   - لا تضف `Client secret` إلى الملف.

4. سجّل الدخول إلى حساب Cloudflare المملوك وانشر Worker بالأداة المثبتة إصدارًا لا نطاقًا:

   ```powershell
   npx wrangler@4.123.0 login
   npx wrangler@4.123.0 secret put GITHUB_CLIENT_SECRET --config workers/sveltia-cms-auth/wrangler.toml
   npx wrangler@4.123.0 deploy --config workers/sveltia-cms-auth/wrangler.toml
   ```

   يُدخل الأمر الثاني السر في مطالبة Cloudflare المشفرة. لا تمرره ضمن سطر الأمر. يجب أن يعرض النشر أصل Worker الملتزم به أعلاه؛ إذا تغير، حدّث رابط الاستدعاء في تطبيق GitHub و`public/admin/config.yml` معًا، ثم التزم بالتعديل وشغّل البوابة الكاملة.

5. في Cloudflare Zero Trust أضف GitHub موفر هوية، ثم أنشئ تطبيق Access من نوع **Self-hosted** للمسار الدقيق `https://ahmed-almangawy.de5.net/admin/*`:

   - السياسة الافتراضية منع.
   - قاعدة السماح لهوية المالك أو بريده الموثق حرفيًا فقط، دون نطاق بريد كامل أو مجموعة عامة.
   - مدة الجلسة الموصى بها أربع ساعات.
   - لا تضع أصل Worker أو مسار `/callback` خلف تطبيق Access؛ فحص المجال داخل Worker يمنع إرسال الرمز إلى أي نافذة غير لوحة الإدارة المسموحة.

6. في GitHub أنشئ Ruleset للفرع `main`: اطلب طلب سحب، واطلب نجاح الفحص الثابت `CMS content gate / cms-content-gate`، وامنع الحذف والدفع القسري والدفع المباشر. احتفظ بتجاوز إداري صريح للمالك للاسترداد الطارئ فقط؛ لا تستخدمه لنشر مقالة فاشلة الفحص.
7. اختبر من نافذة خاصة: يجب أن تظهر بوابة Cloudflare أولًا، ثم زر **تسجيل الدخول باستخدام GitHub** فقط. يجب ألا يظهر خيار رمز الوصول الشخصي. بعد تسجيل الدخول، أنشئ مقالة تجريبية مخفية، وتأكد من إنشاء فرع يبدأ بـ`cms/` وطلب سحب ومنع الدمج حتى ينجح الفحص.

Cloudflare Access وWorkers وPages وGitHub Actions تكفيها الخطط المجانية عادةً لمالك واحد بهذا الاستخدام. نطاق DNSHE الفرعي مجاني، وعلى المالك تجديده في موعده وفق سياسة DNSHE حتى لا يفقده.

### نشر مقالة من اللوحة

1. افتح `/admin/` وسجّل الدخول إلى Cloudflare ثم GitHub بالحساب الوحيد المسموح.
2. اختر **المقالات → إنشاء مقالة**، ثم املأ الحقول العربية. اختر القسم باسمه، وأدخل معرّف يوتيوب المكوّن من 11 حرفًا لا الرابط الكامل.
3. اترك **إبقاء المقالة مخفية بعد الدمج** مفعّلًا أثناء الكتابة. الحفظ ينشئ أو يحدّث طلب سحب؛ لا يجعل المقالة عامة.
4. انتقل في سير العمل من **مسودة** إلى **قيد المراجعة** ثم **جاهز** عند اكتمالها. قبل النشر النهائي ألغِ خيار الإخفاء فقط إذا كانت المقالة صالحة للظهور للعامة.
5. اضغط **نشر** بعد نجاح الفحص المطلوب. يدمج Sveltia طلب السحب ويحذف فرعه، ثم يبني Cloudflare Pages الموقع الثابت من `main`.

الصور المقبولة هي PNG أو JPEG أو WebP حقيقية، بحجم لا يتجاوز 2 ميبيبايت للملف. تُرفض SVG وHTML والملفات ذات الامتداد المضلل، كما تُرفض أي محاولة من فرع `cms/` لتغيير الشفرة أو الإعدادات. إذا فشل الفحص، افتح سجل **Actions** واقرأ أول رسالة خطأ، ثم صحح الحقل أو الصورة من اللوحة واحفظ مجددًا؛ لا تتجاوز الفحص.

حذف مقالة منشورة يمر بطلب سحب أيضًا. لا تحذف فرعًا أو طلبًا من GitHub يدويًا ما دام ظاهرًا في سير العمل التحريري.

### الاسترداد والحوادث

- عند فقد مفتاح المرور، استخدم وسيلة التحقق الاحتياطية أو أحد رموز الاسترداد، ثم ألغِ الوسيلة المفقودة وأنشئ رموزًا جديدة. لا تحل المشكلة بإنشاء رمز وصول شخصي.
- إذا توقفت بوابة الإدارة، تحقق بالترتيب من هوية Access، وقيمة `ALLOWED_DOMAINS`، ورابط `base_url`، ورابط الاستدعاء في GitHub، ثم سجل Worker. لا تغيّر أكثر من قيمة في محاولة واحدة.
- عند الاشتباه باختراق، ألغِ جلسات GitHub وCloudflare وتفويض تطبيق OAuth، ودوّر `Client secret` باستخدام `wrangler secret put`، وافحص طلبات السحب وفروع `cms/` وسجل التدقيق قبل إعادة السماح بالنشر.
- للتراجع عن مقالة دُمجت، أنشئ طلب سحب يعكس التزام الدمج ولا تدفع مباشرة إلى `main`. ولعطل إنتاج كامل استخدم تراجع Cloudflare Pages الموصوف أدناه بينما يُصلح السبب في المستودع.
- إذا تعطّل الفحص المطلوب نفسه ومنع الاسترداد، يستخدم المالك التجاوز الإداري المؤقت مع التزام إصلاح واضح، ثم يعيد الحماية فورًا. لا يُستخدم هذا المسار لتجاوز خطأ محتوى أو ملف مرفوض.

ترقية Sveltia عملية صيانة تقنية: نزّل إصدارًا محددًا، تحقق من سلامة حزمة npm وترخيصها، استبدل `public/admin/sveltia-cms.js`، حدّث البصمة والإصدار في `THIRD_PARTY_NOTICES.md` وسطر المخطط في `config.yml`، ثم أعد التحقق المرئي والبوابة الكاملة. لا تستبدل السكربت برابط CDN غير محدد الإصدار.

## التحقق الاختياري من الأصل النهائي

لا يدخل هذا الفحص في `npm test` أو `npm run verify`، ولا يُشغّل إلا بعد أن يحدد المالك الأصل العام النهائي حرفيًا. استخدم Node.js `24.19.0` وnpm `11.17.0` بالضبط، ثم نفّذ في PowerShell:

```powershell
$approvedOrigin = Read-Host 'أدخل أصل HTTPS النهائي المعتمد'
$env:SITE_ORIGIN = $approvedOrigin
npm run verify:production
Remove-Item Env:SITE_ORIGIN
```

يرفض الأمر القيمة الناقصة أو المحلية أو التي تحتوي مسارًا أو استعلامًا أو جزءًا أو بيانات اعتماد أو منفذًا أو صيغة تحتاج إلى تطبيع. لا تستخدم عنوان معاينة ولا تخمّن اسم المضيف.

بعد انتهاء الفحص، افتح أحدث ملف مطابق للمسار:

```text
.artifacts/phase-06/production/{UTC-run-id}/report.json
```

راجع نطاق الدليل `final-origin` والنقل `network`، والمسارات المختارة، وكل الأخطاء والبوابات. يجب أن يحتوي الفحص الكامل على خمس وظائف للمسارات وثلاث جولات باردة مستقلة لكل وظيفة، أي **15 عينة** خام من LCP وCLS مع وسيط كل مسار. تبقى INP حقيقة حقلية منفصلة.

تقارير `.artifacts/phase-06/controlled/` تثبت صحة الأداة فقط. لا يثبت نجاح فحص محلي أو مضبوط حالة الأصل النهائي، ولا يثبت إنشاء الإطار تشغيل الفيديو، ولا تثبت محاكاة عرض 320 بكسل التكبير الأصلي للمتصفح بنسبة 200%، ولا تثبت نقرة مختبرية INP الحقلي أو الفهرسة أو حالة Cloudflare أو Search Console. بعد المراجعة البشرية فقط حدّث سجل المرحلة السادسة في `.planning/phases/06-production-launch-verification/06-PRODUCTION-EVIDENCE.md`.

## نشر الإنتاج عبر Cloudflare Pages

استخدم مشروع Pages ثابتًا متصلًا بهذا المستودع. اضبط القيم التالية كما هي قبل أول نشر:

| الإعداد                  | القيمة                                            |
| ------------------------ | ------------------------------------------------- |
| فرع الإنتاج              | `main`                                            |
| التحكم في فروع المعاينة  | `None`                                            |
| إصدار Node.js            | `24.19.0`                                         |
| إصدار npm                | `11.17.0`                                         |
| إيقاف التثبيت التلقائي   | `SKIP_DEPENDENCY_INSTALL=1`                       |
| أمر البناء               | `npm ci && npm run check && npm run launch:ready` |
| مجلد المخرجات            | `dist`                                            |
| قيمة البناء العامة للأصل | `SITE_ORIGIN`                                     |

`SITE_ORIGIN` هو الأصل النهائي المملوك بصيغة HTTPS، دون مسار أو استعلام أو جزء. لا تخمّنه ولا تستخدم عنوان نشر Pages المؤقت أو عنوان فرع معاينة أصلًا قانونيًا للموقع. لا يفعّل هذا الإطلاق أي خدمة تحليلات ولا يحتاج إلى قيمة بناء خاصة بها.

### أول نشر وربط النطاق

1. أنشئ مشروع Pages من المستودع، ثم أدخل الإعدادات السابقة واضبط القيم العامة للإنتاج.
2. نفّذ أول نشر وتأكد من أن سجل البناء يعرض `npm ci` ثم فحص Astro ثم بناء `launch-readiness`، وأن الناتج الثابت يأتي من `dist`.
3. أضف النطاق النهائي المملوك من إعدادات النطاقات المخصصة في Pages، ونفّذ سجلات DNS التي يعرضها المزود نفسه.
4. انتظر حتى تصبح حالة النطاق وشهادة TLS فعالتين، ثم اجعل `SITE_ORIGIN` مساويًا للأصل النهائي حرفيًا وأعد النشر.
5. لا تعتبر عنوان Pages المؤقت، أو اسمًا اختباريًا، أو نجاح البناء المحلي دليلًا على ملكية النطاق أو صلاحية DNS أو TLS.

### تشخيص فشل البناء أو النشر

افحص سجل Pages بهذا الترتيب:

1. تأكد من أن Node.js هو `24.19.0` وأن npm هو `11.17.0`؛ يمنع حارس التثبيت أي إصدار آخر.
2. تأكد من ظهور `npm ci` وعدم تشغيل تثبيت تلقائي قبله، ومن بقاء `SKIP_DEPENDENCY_INSTALL=1`.
3. راجع رسالة التحقق من `SITE_ORIGIN`. القيمة الناقصة أو غير الآمنة توقف بناء الإطلاق عمدًا.
4. تأكد من نجاح `npm run check` ومن أن مجلد الإخراج مضبوط على `dist` دون محول خادم أو Worker.
5. إذا نجح البناء وتعذر الوصول، افحص حالة نشر الإنتاج، وربط النطاق، وسجلات DNS، وشهادة TLS في لوحات التحكم المالكة لها.

### التراجع وإعادة النشر

عند تعطل الإنتاج بعد إصدار جديد، افتح قائمة **Deployments** في Pages واختر آخر نشر إنتاج ناجح ثم استخدم التراجع المدمج إليه. لا تغيّر عدة إعدادات أثناء الاستعادة. بعد عودة الموقع، أصلح السبب في المستودع أو إعداد البناء، شغّل البوابة المحلية الكاملة، ثم أعد نشر الالتزام المصحح. إذا كان العطل في قيمة بناء عامة، صحح القيمة في Pages ثم أعد نشر الالتزام نفسه وسجل هوية النشر والوقت في سجل الأدلة.

### فحص هوية النشر بعد كل إصدار

استخدم الأصل النهائي نفسه في كل فحص، ثم سجل النتيجة الفعلية:

1. افتح الصفحة الرئيسة ومقالة منشورة وتأكد من استجابة HTTPS ومن أن `canonical` و`og:url` يستخدمان الأصل النهائي نفسه.
2. افتح `/sitemap-index.xml` وتأكد من أنه يشير إلى خريطة الموقع المطلقة على الأصل نفسه، ثم افحص أن روابط الخريطة عامة ومطلقة.
3. افتح `/robots.txt` وتأكد من أنه يسمح بالزحف ويشير إلى `/sitemap-index.xml` على الأصل نفسه.
4. افحص مصدر الصفحة: يجب ألا يوجد محمّل تحليلات أو مدير وسوم أو أي طلب تتبع خارجي.
5. تأكد من بقاء رابط يوتيوب المباشر رابطًا أصليًا يعمل دون JavaScript ودون وسيط قياس.

## Google Search Console وخريطة الموقع

1. أضف خاصية من نوع **بادئة URL** تساوي `SITE_ORIGIN` النهائي حرفيًا، بما في ذلك `https` واسم المضيف وأي بادئة معتمدة.
2. أكمل إثبات الملكية من السطح المملوك، ويفضل DNS عندما يكون متاحًا. لا تضف رمز تحقق مخمنًا أو ملف تحقق إلى المستودع.
3. في تقرير **Sitemaps** أرسل العنوان المطلق المكوّن من الأصل النهائي متبوعًا بـ`/sitemap-index.xml`.
4. سجل تاريخ الإرسال وآخر قراءة والحالة التي يعرضها Search Console. نجاح الإرسال أو القراءة لا يثبت الفهرسة؛ راقب الفهرسة كحقيقة مستقلة.
